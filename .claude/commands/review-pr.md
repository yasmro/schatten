# review-pr

PR をセルフレビューする。前半のチェックリストは **観察ポイント (input)** で、
網羅的に当てる必要はなく案件に応じて関連するものを取り上げる。後半の出力
フォーマットは **必ずこの順番で出す**。

## Usage

```
/project:review-pr [PR番号]
```

引数がない場合は現在のブランチの PR (または未 push のローカル差分) を対象にする。

## 観察ポイント (Review Checklist)

### 1. コード品質

- [ ] TypeScript の型定義が適切か
- [ ] 不要なコード・コメントが残っていないか
- [ ] 命名規則が既存コードと一貫しているか (`isError` not `invalid`, etc.)

### 2. コンポーネント設計

- [ ] Props API が直感的で一貫しているか
- [ ] `.claude/rules/component-architecture.md` に準拠しているか
  - lv1 / lv2 の配置が責務分離に沿っているか
  - compound vs flat の選択が妥当か (Radix wrap → compound, 自前 → flat, 自前合成は lv2)
  - **新規に `asChild` prop が追加されていないか** (新規 lv1 は default-off。`buttonVariants` / `textVariants` で代替。form input / portal content には何があっても採用不可。既存採用済みコンポーネントの判定は `component-api-conventions.md` §`asChild` を参照)
  - 依存方向が一方向か (`lv1 → lv2` 禁止、`barrel 経由` 禁止、新規 `lib/` utility は 2 consumer 必要)
  - `.css` が raw CSS (`var(--color-*)`) で書かれているか — `@apply` / Tailwind 構文 / primitive の値がないか。component の JSX に Tailwind のユーティリティがないか (§7)。1 コンポーネントに 2 つ目の `.css` を足すなら理由があるか
- [ ] lv2 を追加・変更する場合は `.claude/rules/lv2-composition-guideline.md` に準拠しているか
  - 昇格基準 (G1–G4 / D1–D3) の判定結果が issue / PR 説明に書かれているか
  - flat + curated props か (compound になっていないか)、独自 React Context を provide していないか
  - 公開クラスが block + modifier だけか (sub-element を公開するなら消費者ユースケースが PR 説明にあるか)
  - React 専用の前提を崩していないか (parity / vanilla harness / `CSSApiDist` fixture を足していないか、内部の DOM を素の HTML 向けに約束していないか)
  - 自前の primitive (semantic な要素・Radix・context) を持ち込んでいないか (`component-architecture.md` §1)
- [ ] Context 連携パターンに従っているか (`.claude/rules/field-context-guideline.md` 参照)
  - 内部ラベルありコンポーネント: `field?.id` を使わない
  - 内部ラベルなしコンポーネント: `field?.id` を使う
- [ ] Fallback パターン: `field?.value ?? propValue ?? defaultValue`
- [ ] standalone / Field 内両方で動作するか

### 3. デザインシステムの堅牢性

- [ ] デザイントークン (CSS 変数) を使用しているか (ハードコード値を避ける)
- [ ] 既存コンポーネントと variant/size の命名が一貫しているか
- [ ] CVA パターンに従っているか (`src/variants/` に定義)
- [ ] 類似コンポーネントと Props API が統一されているか
  - 例: `isError`, `disabled`, `size` の命名と型
- [ ] スペーシング・タイポグラフィが Tailwind のスケールに沿っているか
- [ ] ダークモード対応: `text-foreground`, `bg-background` などセマンティックカラーを使用
- [ ] 破壊的変更がないか (既存 API の互換性 — `.claude/rules/api-stability.md` 参照)

### 4. アクセシビリティ (a11y)

- [ ] `aria-*` 属性が適切に設定されているか
- [ ] `aria-describedby` で description/error がリンクされているか
- [ ] `aria-invalid` がエラー時に設定されているか
- [ ] キーボード操作が可能か
- [ ] フォーカス管理が適切か

### 5. Storybook

- [ ] `Playground` story が最初にあるか
- [ ] `argTypes` の description が正確か (実際の挙動と一致)
- [ ] 必要なパターンが網羅されているか (variants, sizes, states)
- [ ] 英語で記述されているか

### 6. テスト

- [ ] 主要な機能にテストがあるか
- [ ] Context 連携のテストがあるか
- [ ] エッジケースが考慮されているか

### 7. ドキュメント

- [ ] PR body が最新の実装を反映しているか
- [ ] 必要に応じて Claude rules が更新されているか

## 出力フォーマット

以下 3 セクションを **この順番** で出力する。セクションを省略しない、順番も変えない。

### 1. 3 つの目線でのレビュー

#### ①スタッフエンジニア目線

技術的な堅牢性 / 保守性 / 変更容易性 / 設計判断を評価する。観点 (上の Checklist §1〜2, §6
を参照しつつ、案件に応じて関連するものを取り上げる):

- アーキテクチャ判断の妥当性と代替案との比較 — なぜこの形を選んだか、見送った
  選択肢の trade-off は何か
- 実装の正しさ — 抽象化の漏れ、edge case、競合状態、エラーパス
- 本番 contract への影響 — 公開 API・CSS class・CSS var・型・peer dep の互換性
- テスト / CI シグナルの質 — 「カバレッジ % ではなく "壊れたら検知できるか"」
- 依存方向と層の責務 (`.claude/rules/component-architecture.md` §6)
- 保守コスト — 6 ヶ月後の自分 / 他人が読んで理解できるか
- 変更容易性 — 次に要件が変わったとき、どこまで手を入れることになるか
  - 波及範囲 — 1 つの変更で触るファイル・baseline・消費者が局所に収まるか
  - 可逆性 — 公開面を増やす判断は後から戻せないので、最小で始めて後から足せる形か
    (`.claude/rules/api-stability.md`)
  - 差し替えやすさ — 外部依存の都合が公開型や class に漏れず、境界の内側で吸収できるか
  - テストの支え — 実装の細部ではなく振る舞いを見ていて、リファクタで不要に壊れないか
- 観測性 — log / warn の場所が適切か

末尾に **「👍 良いところ」** と **「🤔 改善余地」** を箇条書きで分け、最後に
**評点 (N/10) と一文サマリ**。

#### ②デザインストラテジスト目線

デザインシステムとしての価値 / スケーラビリティ / ガバナンスを評価する。観点
(上の Checklist §3〜5, §7 を参照しつつ):

- このデザインシステムの宣言された原則 (二軸モデル / Pattern A・B / state token
  shape など) に整合しているか、原則そのものを強化しているか
- スケーラビリティ — Special / variant / consumer / contributor が N 倍に
  増えたとき摩擦はどう動くか
- ブランド / 文化資産 (二十四節気・和の色彩) との整合
- 教育的価値 — 新規参加者 (engineer / designer) が暗黙知を学ぶ場として機能するか
- a11y / inclusivity — WCAG だけでなく "誰が読み書きできるか" の視点
- 意思決定支援 — このコンポーネント / story を使う人が次の判断を素早くできるか
- ガバナンス — 「variant を追加する人」「component を提案する人」の動線が
  明示されているか

末尾に同じく **「👍」「🤔」「評点 (N/10) と一文サマリ」**。

#### ③ブランディングアーティスト目線

**実際に描画された画像を見て**、Schatten らしい仕上がりかを評価する。①②が
「どう作ったか」を読むのに対し、③は「何が見えているか」だけを見る。VRT が
「ピクセルが動いたか」を確かめるのとも役割が違う。判断の基準は好みではなく
[docs/brand-concept.md](../../docs/brand-concept.md) に置く。

手順は下の「ブランドレビューの進め方」に従う。観点:

- **紙と墨の階調** — 面と文字の差を、純白・純黒ではなく寒暖の階調で作れているか
  (§2.1, §3.4)。立体感を `box-shadow` に頼っていないか
- **朱と藍** — 朱が「警告」に読めないか。紅と並べて別の色に見えるか (§3.1)。
  二色が静かな面に許された差し色に収まり、面積で主張しすぎていないか
- **八節** — 季節を替えても、文字の読みやすさと情報の階層が動いていないか (§3.3)
- **組版** — 書体の対・ウェイト・行送り・余白のリズムが既存の画面と揃っているか
  (§1.6)
- **系としての一体感** — 既存コンポーネントと並べて同じ家族に見えるか。密度・
  角の扱い・線の太さに、そこだけ別の手が入った感じがないか

末尾に同じく **「👍」「🤔」「評点 (N/10) と一文サマリ」**。各指摘には **画像の
ファイル名と画面上の位置** を添える。根拠を示せない所感は「好み」と明記する。

視覚に関わる変更がない PR では、③は「**対象外** (理由: <変更の種類>)」の 1 行に
して評点を付けない。撮影に失敗した場合は「**未実施** (理由)」と書き、コードから
見た目を推測して埋めない。

### 2. マージ可否の評価

以下 3 段階のどれかで明示する:

- **✅ Ship** — そのままマージ可。残課題は別 PR / 別 issue で対応すべき。
- **🟡 Ship with notes** — マージはしてよいが、レビュアー / 著者が認識すべき
  事項がある (CHANGELOG への追記、フォローアップ issue の作成、など)。具体的な
  notes を箇条書き。
- **🔴 Block** — 現状ではマージすべきでない。最低限直すべき項目を **必須 (must)
  と望ましい (should) に分けて** 箇条書き。

判断根拠は 2–3 文で添える。「3 つの目線」の評点を足して機械的に決めるようなことは
しない — 評点はあくまで補助で、merge 判定は scope と risk のホリスティック判断。
③だけを理由に Block するのは、brand-concept の主張に反すること (朱が危険色として
使われている、季節が可読性を動かしている など) をコードでも確認できた場合に限る。
美的な指摘は 🟡 の notes か §3 のレコメンドに回す。

### 3. 次の改善レコメンド (優先度順)

以下フォーマットで P0 / P1 / P2 に分類。**最大でも 5 項目まで** に絞る (薄い
レコメンドを並べると行動につながらない)。

```
### P0: <タイトル>
- **やること:** <1–2 文で具体的に>
- **やらない場合:** <どんな問題が、いつ顕在化するか — 簡潔に>

### P1: ...
### P2: ...
```

**P0 = 次の PR 又は本 PR 内で対応すべき**、
**P1 = 同じマイルストーン内に解決したい**、
**P2 = ロードマップに乗せておきたいが今すぐではない**。

「全部やるべき」と言わないことが重要 — それぞれの **やらない場合** を正直に書き、
ユーザが scope cut できる材料を渡す。**実際に "今はやらない" 判断もアリ** で、
その場合は最終行に「**推奨: 全項目とも今は着手しない (理由: ...)」と書く。

## Instructions

1. 対象差分の取得
   - 引数あり: `gh pr view [番号] --json title,body,files` + `gh pr diff [番号]`
   - 引数なし: `gh pr view --json title,body,files` を試し、なければ
     `git diff origin/main...HEAD` でローカル差分を見る
2. 「観察ポイント」のチェックリストを参考に、変更の中心となるファイルを Read で
   熟読する (全 file を grep するより理解優先)。関連する `.claude/rules/*.md`
   も必要に応じて読む
3. 「ブランドレビューの進め方」に従って③の材料を用意する
4. 上記「出力フォーマット」の 3 セクションを **順番通り** に出力する
5. レビュアーが追加質問しなくても **判断根拠と trade-off** が読み取れる粒度
   で書く

## ブランドレビューの進め方

1. **撮影**: `pnpm review:shots` を実行する (比較元が develop 以外なら
   `--base <ref>`、見たい story を指定するなら `--stories <id,id>`)。空きポートで
   このブランチ専用の Storybook を起動し、変更に対応する story を `.review-shots/`
   に書き出す。1 story につき light / dark / 春 (light) / 冬 (dark) の 4 枚で、最大
   6 story。`manifest.json` の `visualFiles` が空なら③は対象外なので、ここで終える。
2. **別の目で見る**: 差分を読んだ本人は意図に引きずられるので、Agent ツール
   (`general-purpose`) で fresh な agent を起動し、下のブリーフをそのまま渡す。
   **PR の説明・差分・実装の意図は渡さない**。これが③の価値で、画像も親の
   コンテキストに載らずに済む。Agent を使えない環境では自分で画像を読み、③の冒頭に
   「差分を読んだ本人が判定」と書く。
3. **裏を取る**: 返ってきた指摘は仮説として扱う。色や token に関する指摘は、画像の
   見た目だけで確定せず、コードで確かめてから③に載せる。確かめられなければ
   「未確認」と添える。`manifest.json` の `omitted` / `failed` があれば、③に
   「見ていない story」として書く。`duplicates` はテーマ指定が効かなかった story
   なので、季節の評価から外す。

### agent に渡すブリーフ

```
あなたは Schatten デザインシステムのブランディングアーティストです。実装の
背景は知らされていません。見えているものだけで評価してください。

1. docs/brand-concept.md を読む。§2 のテーゼと §3 の各論が判断基準です。
2. .review-shots/manifest.json を読み、shots の file をすべて Read ツールで見る。
   before があるものは before も見て、何が変わったかを確かめる。
3. 次の観点で評価する: 紙と墨の階調 / 朱と藍の扱い / 季節を替えたときの読みやすさ
   と階層 / 組版と余白のリズム / 既存の系との一体感。

ルール:
- 指摘には画像のファイル名と画面上の位置を必ず添える。画像を読まずに書かない。
- 基準は brand-concept に置く。根拠を示せない所感は「好み」と明記する。
- コードは読まない。色の値を断定せず「〜に見える」と書く。
- 静止画なので hover / focus / 動きは判定しない。story は英語中心なので、和文組版
  も判定しない。before は VRT baseline で切り抜き範囲が違うことがあり、構図の差は
  変更として扱わない。
- 良い点も同じ粒度で書く。
- 🤔 は重要な順に最大 5 件に絞る。今回の変更と無関係な既存の問題は別枠に 1 行で書く。

出力: 👍 良いところ / 🤔 改善余地 / 評点 (N/10) と一文サマリ
```
