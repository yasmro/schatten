# review-pr

PR をセルフレビューする。前半のチェックリストは **観察ポイント (input)** で、
網羅的に当てる必要はなく案件に応じて関連するものを取り上げる。後半の出力
フォーマットは **必ずこの順番で出す**。

## Usage

```
/project:review-pr [PR番号]
```

引数がない場合は現在のブランチの PR (または未 push のローカル差分) を対象にする。

## 観察ポイント (Review Checklist)

### 1. コード品質

- [ ] TypeScript の型定義が適切か
- [ ] 不要なコード・コメントが残っていないか
- [ ] 命名規則が既存コードと一貫しているか (`isError` not `invalid`, etc.)

### 2. コンポーネント設計

- [ ] Props API が直感的で一貫しているか
- [ ] `.claude/rules/component-architecture.md` に準拠しているか
  - lv1 / lv2 の配置が責務分離に沿っているか
  - compound vs flat の選択が妥当か (Radix wrap → compound, 自前 → flat, 自前合成は lv2)
  - **新規に `asChild` prop が追加されていないか** (新規 lv1 は default-off。`buttonVariants` / `textVariants` で代替。form input / portal content には何があっても採用不可。既存採用済みコンポーネントの判定は `component-api-conventions.md` §`asChild` を参照)
  - 依存方向が一方向か (`lv1 → lv2` 禁止、`barrel 経由` 禁止、新規 `lib/` utility は 2 consumer 必要)
  - 新規ファイルとして `.css` が増えていないか — 増えている場合は Tailwind/CVA で表現困難な理由があるか
- [ ] Context 連携パターンに従っているか (`.claude/rules/field-context-guideline.md` 参照)
  - 内部ラベルありコンポーネント: `field?.id` を使わない
  - 内部ラベルなしコンポーネント: `field?.id` を使う
- [ ] Fallback パターン: `field?.value ?? propValue ?? defaultValue`
- [ ] standalone / Field 内両方で動作するか

### 3. デザインシステムの堅牢性

- [ ] デザイントークン (CSS 変数) を使用しているか (ハードコード値を避ける)
- [ ] 既存コンポーネントと variant/size の命名が一貫しているか
- [ ] CVA パターンに従っているか (`src/variants/` に定義)
- [ ] 類似コンポーネントと Props API が統一されているか
  - 例: `isError`, `disabled`, `size` の命名と型
- [ ] スペーシング・タイポグラフィが Tailwind のスケールに沿っているか
- [ ] ダークモード対応: `text-foreground`, `bg-background` などセマンティックカラーを使用
- [ ] 破壊的変更がないか (既存 API の互換性 — `.claude/rules/api-stability.md` 参照)

### 4. アクセシビリティ (a11y)

- [ ] `aria-*` 属性が適切に設定されているか
- [ ] `aria-describedby` で description/error がリンクされているか
- [ ] `aria-invalid` がエラー時に設定されているか
- [ ] キーボード操作が可能か
- [ ] フォーカス管理が適切か

### 5. Storybook

- [ ] `Playground` story が最初にあるか
- [ ] `argTypes` の description が正確か (実際の挙動と一致)
- [ ] 必要なパターンが網羅されているか (variants, sizes, states)
- [ ] 英語で記述されているか

### 6. テスト

- [ ] 主要な機能にテストがあるか
- [ ] Context 連携のテストがあるか
- [ ] エッジケースが考慮されているか

### 7. ドキュメント

- [ ] PR body が最新の実装を反映しているか
- [ ] 必要に応じて Claude rules が更新されているか

## 出力フォーマット

以下 3 セクションを **この順番** で出力する。セクションを省略しない、順番も変えない。

### 1. 2 つの目線でのレビュー

#### ①スタッフエンジニア目線

技術的な堅牢性 / 保守性 / 設計判断を評価する。観点 (上の Checklist §1〜2, §6
を参照しつつ、案件に応じて関連するものを取り上げる):

- アーキテクチャ判断の妥当性と代替案との比較 — なぜこの形を選んだか、見送った
  選択肢の trade-off は何か
- 実装の正しさ — 抽象化の漏れ、edge case、競合状態、エラーパス
- 本番 contract への影響 — 公開 API・CSS class・CSS var・型・peer dep の互換性
- テスト / CI シグナルの質 — 「カバレッジ % ではなく "壊れたら検知できるか"」
- 依存方向と層の責務 (`.claude/rules/component-architecture.md` §6)
- 保守コスト — 6 ヶ月後の自分 / 他人が読んで理解できるか、変更が局所化されているか
- 観測性 — log / warn の場所が適切か

末尾に **「👍 良いところ」** と **「🤔 改善余地」** を箇条書きで分け、最後に
**評点 (N/10) と一文サマリ**。

#### ②デザインストラテジスト目線

デザインシステムとしての価値 / スケーラビリティ / ガバナンスを評価する。観点
(上の Checklist §3〜5, §7 を参照しつつ):

- このデザインシステムの宣言された原則 (二軸モデル / Pattern A・B / state token
  shape など) に整合しているか、原則そのものを強化しているか
- スケーラビリティ — Special / variant / consumer / contributor が N 倍に
  増えたとき摩擦はどう動くか
- ブランド / 文化資産 (二十四節気・和の色彩) との整合
- 教育的価値 — 新規参加者 (engineer / designer) が暗黙知を学ぶ場として機能するか
- a11y / inclusivity — WCAG だけでなく "誰が読み書きできるか" の視点
- 意思決定支援 — このコンポーネント / story を使う人が次の判断を素早くできるか
- ガバナンス — 「variant を追加する人」「component を提案する人」の動線が
  明示されているか

末尾に同じく **「👍」「🤔」「評点 (N/10) と一文サマリ」**。

### 2. マージ可否の評価

以下 3 段階のどれかで明示する:

- **✅ Ship** — そのままマージ可。残課題は別 PR / 別 issue で対応すべき。
- **🟡 Ship with notes** — マージはしてよいが、レビュアー / 著者が認識すべき
  事項がある (CHANGELOG への追記、フォローアップ issue の作成、など)。具体的な
  notes を箇条書き。
- **🔴 Block** — 現状ではマージすべきでない。最低限直すべき項目を **必須 (must)
  と望ましい (should) に分けて** 箇条書き。

判断根拠は 2–3 文で添える。「2 つの目線」の評点を足して N/20 で機械的に決める
ようなことはしない — 評点はあくまで補助で、merge 判定は scope と risk の
ホリスティック判断。

### 3. 次の改善レコメンド (優先度順)

以下フォーマットで P0 / P1 / P2 に分類。**最大でも 5 項目まで** に絞る (薄い
レコメンドを並べると行動につながらない)。

```
### P0: <タイトル>
- **やること:** <1–2 文で具体的に>
- **やらない場合:** <どんな問題が、いつ顕在化するか — 簡潔に>

### P1: ...
### P2: ...
```

**P0 = 次の PR 又は本 PR 内で対応すべき**、
**P1 = 同じマイルストーン内に解決したい**、
**P2 = ロードマップに乗せておきたいが今すぐではない**。

「全部やるべき」と言わないことが重要 — それぞれの **やらない場合** を正直に書き、
ユーザが scope cut できる材料を渡す。**実際に "今はやらない" 判断もアリ** で、
その場合は最終行に「**推奨: 全項目とも今は着手しない (理由: ...)」と書く。

## Instructions

1. 対象差分の取得
   - 引数あり: `gh pr view [番号] --json title,body,files` + `gh pr diff [番号]`
   - 引数なし: `gh pr view --json title,body,files` を試し、なければ
     `git diff origin/main...HEAD` でローカル差分を見る
2. 「観察ポイント」のチェックリストを参考に、変更の中心となるファイルを Read で
   熟読する (全 file を grep するより理解優先)。関連する `.claude/rules/*.md`
   も必要に応じて読む
3. 上記「出力フォーマット」の 3 セクションを **順番通り** に出力する
4. レビュアーが追加質問しなくても **判断根拠と trade-off** が読み取れる粒度
   で書く
