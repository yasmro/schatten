# AI-DLC は本体に入れず、必要なときだけ別コピーで動かす

- **Status**: Accepted
- **Date**: 2026-09-03
- **Related**: [#526](https://github.com/yasmro/schatten/issues/526)（この調査） /

- **調べ方**: `awslabs/aidlc-workflows` の **tag `v2.7.0`** を取得し、
  **Schatten の使い捨てコピーに実際にインストールして1件動かした**（資料を読んだだけではない）

## なぜ調べたか

AWS が公開している AI-DLC という開発の進め方を、Schatten に取り込めるかを調べた。
問いは「入れるか入れないか」ではない。**「今の進め方のどこが手薄で、そこを埋められるか」**である。

Schatten には15回のリリースを通して育ってきた4層の仕組みがある。ルール12本、AI 用の補助6種、
編集時に動く見張り2本、そして PR を止める CI の9ジョブ。そこへ別系統の進め方をそのまま重ねれば、二重になる。だから重なりを先に測る必要があった。

**この記録は2回目の調査結果である。** 1回目（PR #536、取り下げ済み）は資料を読んだだけで
「入れずに考え方だけ3つ持ち込む」と結論した。だが次の3点でまちがっていた。

1. AWS の Bedrock が必須だと誤読し、導入コストを高く見積もった
2. 33ある工程の価値を、判断基準を書かないまま感覚で仕分けた
3. #526 が最初に挙げている目的「実際に触って学ぶ」を、構造的に果たせない結論だった

今回は #526 の論点5（実際に1件動かす）を飛ばしていない。

## どう確かめたか

**環境**: Schatten の `develop` を使い捨てにコピーし、そこに AI-DLC を入れた。本体は無変更。
`bun` は一時フォルダに閉じ込め、インストーラが `~/.zshrc` に足した行は戻した。

**題材**: **#492（lv2 のルール作り）**。#526 が候補に挙げていたもので、
「何を作るか決める」という、今の進め方がいちばん手薄な段階にあたる。

**比較相手**: #492 には、すでに今のやり方（`refinement-issue`）で書いた設計が入っている
（444行）。つまり同じ題材で二つのやり方を並べられる。

**公平さの担保**: AI-DLC 側のエージェントには、**#492 とその設計を読むことを禁じた**。ゼロから考えさせた。

**比べる観点**: #526 の指定どおり、始める前に4つ決めた。かかった時間、出てきたものの中身、
既存ルールとの噛み合い、人が判断を求められる回数。

## わかったこと

### 準備でつまずいた4点。うち1つは気づけない

| # | 何が起きたか | 重さ |
|---|---|---|
| 1 | `bun` のインストーラが **`~/.zshrc` を勝手に書き換えた** | 軽い（戻せる） |
| 2 | **ファイルをコピーすると `.claude/settings.json` が上書きされ、Schatten の見張り2本が黙って消える** | **重い**。公式手順は「混ぜろ」と書いてあるが、失敗しても何も言われない |
| 3 | `.claude/` だけコピーすると診断が1件落ちる（作業フォルダのコピー漏れ） | 軽い（診断が教えてくれる） |
| 4 | ルールの配布は編集フックが前提。フックの効かない外から動かすと、手で渡す必要がある | 中くらい |

**診断コマンドは Bedrock なしで50項目すべて通った。** 1回目の「Bedrock が必須」は**まちがい**である
（公式の原文は「そのまま使うなら必要」という条件付きで、AI-DLC 本体で Bedrock に触れているのは
87ファイル中2つだけ）。

### 規模の縮小は実際に効く

用意されている11の型はどれも当てはまらなかった。「ルールを決める」という作業に対応する型がないためである。
そこで AI-DLC は**その場で専用の型を組み立てた**。結果は **33工程のうち11を実行、22を省略、人の承認は8回**。
省略した22すべてに個別の理由が付いている。

### 出てきたもの — 得意分野がはっきり分かれた

**今のやり方が勝つ領域: 実装の細かさ**

同じ問題（lv2 が CI をすり抜ける件）について、両者の書きぶりを並べる。

| | AI-DLC | #492 にある既存の設計 |
|---|---|---|
| 直す場所 | 1か所 | **2か所とも特定** |
| 影響範囲 | ふれただけ | **11ファイルの変更表** |
| 気づきにくい点 | なし | 似た関数どうしの挙動の食い違い、Storybook の設定は変えなくてよい理由、容量制限を上げるなら changeset が要ること |

昇格の判定についても、既存の設計には**4つの関門と、部品ごとの判定表**があり、
同じ趣旨の指摘でも、向こうより細かい。ADR-0010 との線引きにも専用の節がある。

**AI-DLC が勝つ領域: 前提そのものを疑う**

既存の設計が出せていない指摘が4つ出た。**すべて裏を取ってある。**

| # | 指摘 | 確認結果 |
|---|---|---|
| 1 | 最初に作る3つは「よく使う組み合わせの格上げ」ではなく**まったくの新規**で、#492 が前提にしている枠組みと合っていない | ✅ `ConfirmDialog` / `EmptyState` / `PageHeader` の名前は `src/` `docs/` `examples/` に**1回も出てこない**。既存の設計は「よく使われている」を OK としているが根拠がない |
| 2 | **PageHeader は基準を通すべきではない**（レシピ集に置くべき） | 既存の設計は3つとも作る前提。設計上の異論 |
| 3 | ルールに矛盾がある。「複数箇所に中身を差し込むなら lv2」と書いてあるのに `Card` は6か所差し込めて lv1 のまま | ✅ `component-architecture.md` の76〜77行目に該当記述あり |
| 4 | ドキュメントの数字がずれている | ✅ `api-stability.md` の538行目は「lv1 は18個」だが**実際は25個**。`PARITY_EXEMPT` のコメントは「7個」だが**中身は8個** |

さらに、ルールが lv2 の代表例として挙げている `FormField` が、AI-DLC の新しい基準の失格条件に
自分で当てはまるという指摘も出た（`Field` がすでにほぼ同じことをしている）。

**この差は偶然ではない。** 向こうは「設計判断には**最低2案の比較**を書け」
「判断記録には Context / Decision / Consequences / **却下した案**を必ず含めろ」を機械的に課す。
上の1と2は、その「他の案は」「本当にこの枠組みでよいのか」という強制からそのまま出ている。

### かかったコスト

| | AI-DLC | 今のやり方 |
|---|---|---|
| **人が判断を求められる回数** | **8回**（33工程のうち27が「人の承認が必須。推測も自動承認も省略も不可」と定められている） | **1回**（起動して出力を1本受け取り、最後に読む） |
| **時間** | **48分**（11工程のうち2つ) | 1回の起動 |
| **トークン** | **825,185** | 1回分 |
| **出てきた量** | 2,617行 / 131,776字（7ファイル、2工程分） | 444行 / 22,787字（完成した設計） |

### 同居させた場合のコスト

**見張りは安全である。** 付属の見張りは、自分の作業が動いていないときは何もしない
（`aidlc-continue-workflow.ts` の冒頭に「AI-DLC の外では何もしない。AI-DLC でないセッションは
決して止めない」と明記）。Schatten の通常作業に干渉しない。

**置き場所は重なる。** `.claude/` に277ファイル・5.8MB が入る。ルールは12本から13本、
**使えるコマンドは6個から48個**になる。

**本当の導入作業はファイル数ではない。** 空のテンプレート（`team.md` / `project.md`、
合わせて約50行）に Schatten の規約を書くことである。付属の初期設定は Schatten と5点食い違う
（`main` に直接まとめる前提、Prettier、ESLint、テスト網羅率80%の下限など。Schatten は
`develop` 経由、Biome、[網羅率の目標は明示的に置かない](../../.claude/rules/testing-guideline.md)）。
ただし**書いてある層が勝つ**仕組みなので解消できる。

**ただし罠がある。** 向こうは「Schatten の規約は暗黙知ではなく文書化済み」という**正しい理由**で、
規約を聞き取る工程を省略する。ところがその工程が `team.md` を埋める唯一の自動経路である。
省略すると初期値（`main` に直接）がそのまま効く。仕組み自体は検知して警告を出すので、
気づけないわけではない。導入する人が手で埋める必要がある、ということである。

### この調査の限界

動かしたエージェントは**この作業と同じモデル**であり、Schatten の実ファイルを読んでいる。
出てきたものの質が *AI-DLC の進め方* から来たのか、*賢いモデルが文書化されたルールを読んだこと* から
来たのかは、完全には切り分けられていない。ただし指摘1と2が「最低2案」「却下した案」という
**機械的な強制のすぐ下から出ている**。この点を見るかぎり、進め方そのものが効いていると考えてよい。

## 決めたこと

**AI-DLC を Schatten 本体には入れない。**
**代わりに (a) 長く保持する別コピーを1つ用意して「上流の判断のセカンドオピニオン」として使い、
(b) 価値の源になっている2つの規律を今の補助に持ち込む。**

目的は #526 の **A（学ぶ）+ B（穴を埋める）**。C（置き換え）は採らない。

## そう決めた理由

1. **役に立つことは確認でき、その場所も特定できた。** AI-DLC は*枠組みを疑う*役割で今のやり方に勝ち、
   裏の取れた見落としを4件出した。1回目の「価値が薄い」寄りの結論はまちがいだった。
2. **ただしその価値に、本体への設置は要らない。** 今回それを使い捨てコピーで得ている。
   見張りが何もしない以上、入れても害は小さい。だが**得るものもない** —
   AI-DLC が読むのはリポジトリのファイルであって、自分がその中にいる必要はない。
3. **入れると失うものがある。** コマンド一覧が6個から48個に膨らむ負担は毎回効く。
   加えて Schatten の資産価値は[他所でも使える進め方](../../CLAUDE.md)を示すことにあり、
   5.8MB の外部ツールが同居するとその主張が弱まる。
4. **実装とリリースの工程は重なる**（14工程）。しかも Schatten 側は PR を止める CI が9本、
   向こうの検査は**実測で6種すべて「助言」止まり**。置き換えれば強度が下がる。
5. **日常使いには重い。** 承認8回・48分・82万トークンは、`refinement-issue` 1回と釣り合わない。
   **常用ではなく、必要なときのセカンドオピニオン**が適した使い方である。

## 検討して却下した案

この記録が提案している規律（却下した案を書く）を、この記録自身にも適用する。

| 案 | 却下の理由 |
|---|---|
| **本体にそのまま入れる** | 見張りが何もしない以上、実害は小さい。だがコマンド一覧が8倍になる負担が毎回効き、外部ツール同居で Schatten の主張が弱まる。得られる価値は別コピーで取れており、設置で増えるものがない |
| **上流の工程だけ切り出して持ち込む** | **構造上できない。** 配布物の42個の補助はすべて中核エンジンを呼ぶ薄い包み紙で、1工程動かすにも一式（ツール69・見張り18・共通42・知識59）が要る |
| **今の進め方を AI-DLC に寄せる（置き換え）** | 実装とリリースの工程は Schatten 側のほうが強度が高い（PR を止める CI 9本 対 助言止まりの検査6種）。さらに AI-DLC が「聞き取る」対象の規約が、Schatten では既に12本の文書になっている。置き換えは資産の破棄になる |
| **使い捨てコピーを毎回作る** | 準備に毎回15分ほどかかる。長く保持する1つを `develop` から更新するほうが安い |

## (a) 別コピーの運用

`schatten-aidlc` という長期のコピーを1つ持ち、`develop` から随時更新する。
準備は一度きり（設定ファイルの統合、`team.md` / `project.md` に Schatten の規約、
初期設定の5点の食い違いを上書き）。新しいルールを決める、マイルストーンを設計する、
アーキテクチャを判断するといった重い場面で、別の見方が欲しいときに回す。

## (b) 持ち込む2つの規律

| # | 規律 | 持ち込み先 | 根拠 |
|---|---|---|---|
| 1 | **「最低2案の比較と、却下した案の明示」を成果物の形式として必須にする** | `refinement-issue` と [docs/decisions/README.md](README.md) の必須項目 | 今回の指摘1と2はこの強制の直下から出た。Schatten の判断記録は「理由」は書くが、**却下した案を必須にしていない** |
| 2 | **入力と出力を宣言して、依存関係を機械的に導けるようにする** | `refinement-version` | エンジンは122の成果物とつながりを機械検証し、前提の揃わない工程の単独実行を正しく拒否した。`refinement-version` は今、issue の本文から依存を**推測**している |

レビューの強さを成果物ごとに宣言する仕組みも候補に残すが、1と2の後にする。

## 結果として起きること

**良いこと**: 今の4層の仕組みは無傷。価値は別コピーで取れる。持ち込む2規律は、
今の補助の実証済みの弱点（却下案が残らない、依存が推測頼み）にそのまま当たる。
副産物として **Schatten 側の実在する欠陥が4件**見つかり、すぐ直せる。

**悪いこと**: 別コピーは使うたびに更新の手間がある。本体に入れていれば常に手元にある。
**使う回数が増えればこの判断は見直すべきである。**目安として、半年で3回以上回すなら本体設置を再評価する。

**限界**: 11工程のうち**2つ**しか動かしていない。実装とリリースの工程は未実行だが、
そこは Schatten 側が厚く、重複と判定済み。同じモデルを使った交絡は上記のとおり未解消。

## 次にやること

1. **今回見つかった Schatten 側の欠陥を直す**（AI-DLC と関係なく価値がある）:
   `component-architecture.md` の矛盾、`api-stability.md` の「18個」→25個、
   `PARITY_EXEMPT` のコメント「7個」→8個、そして **lv2 が CI を素通しする件**（#492 に反映）
2. **規律1（却下した案を必須にする）** を [docs/decisions/README.md](README.md) の形式と
   `refinement-issue` に入れる
3. **規律2（入力と出力の宣言）** を `refinement-version` に入れる
4. **別コピーを常設する**（`schatten-aidlc`）と、準備手順を記録する

**やらないこと**: 配布物の本体設置、今の4層の置き換えや撤去、他のツールへの横展開。
